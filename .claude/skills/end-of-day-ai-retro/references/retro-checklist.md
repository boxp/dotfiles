# リフレクションチェックリスト

## セッション観察チェックリスト

### 1. 繰り返し指示

- 毎回同じ前置きや制約を書いたか
- 毎回同じ確認質問が出たか
- 毎回同じファイルやドキュメントを明示的に読ませたか

この系統は `rules`、`skill`、`CLAUDE.md`、project doc に昇格できる可能性が高い。

### 2. 実行環境の摩擦

- 作業ディレクトリを間違えたか
- worktree / branch / repo の選択で迷ったか
- 承認、sandbox、ネットワーク制約で止まったか
- 通知が弱く、完了に気づきにくかったか

この系統は起動方法、tmux、hook、通知、worktree 運用の見直し候補。

### 3. 出力品質の摩擦

- レビュー観点が浅かったか
- 実装前の計画が弱かったか
- 最終回答の粒度が揺れたか
- 日本語/英語、箇条書き、要約形式が安定しなかったか

この系統は skill 本文、default prompt、共通 instruction の見直し候補。

### 4. 情報収集の摩擦

- 毎回同じ社内情報源を探したか
- 参照先は決まっているのに探索コストが高かったか
- Confluence / Jira / Glean / GitHub のどこを見るべきか迷ったか
- Langfuse trace を見れば分かることを、感覚や記憶だけで判断していないか

この系統は専用 skill、検索テンプレート、参照順序の明文化候補。

### 5. Langfuse trace の摩擦

- latency が高い trace はどれか
- token 使用量が大きい trace はどれか
- retry / error / warning が繰り返されていないか
- name / sessionId / tag の付け方が弱く、あとから追いにくくないか

この系統は tracing 設計、タグ設計、skill 事前確認、プロンプトの分割候補。

## 変更施策の分類

### グローバル設定に向くもの

- 複数 repo で再発する
- 毎日使う
- 失敗時のコストが高い

例:
- `~/.codex/config.toml`
- `~/.codex/rules/*.rules`
- `~/.claude/CLAUDE.md`
- 通知 hook

### repo ローカルに向くもの

- 特定 repo の構成や運用に依存する
- 特定チームのルールに閉じる
- 共有するとノイズが増える

例:
- repo の `AGENTS.md`
- `.claude/skills/<repo-specific-skill>`
- `docs/project_docs/...`

## 提案の優先順位付け

### P1

- 明日からすぐ効く
- 変更が小さい
- 誤爆しにくい

### P2

- 効果は高いが、skill や rules の設計が必要

### P3

- 効果が不確実
- 継続観察が必要
